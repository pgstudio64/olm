## 1. Synthèse exécutive

### 1.1 Verdict global

Le code OLM est **solide dans son cœur métier** (`olm/core/`) et **fragile dans ses couches d'orchestration** (`olm/server/app.py`, `olm/ingestion/extract.py` ↔ `test_comb.py`). Le schéma canonique de pièce est cohérent, testé en round-trip côté JS, et bien documenté dans plusieurs specs. La qualité Python (docstrings, dataclasses, séparation des modules cœur) est au-dessus de la moyenne d'un prototype. Le front-end vanilla JS est bien organisé pour sa taille (~14 700 lignes) grâce au pattern `olmStore` (`store.js`) et au helper `room_sync_helpers.js`. Les recommandations des audits 2026-04-21 ont été **largement appliquées**.

En contrepartie, **cinq dettes structurelles** plombent la trajectoire :

1. **Aucun test sur ~5 300 lignes critiques** (`extract.py` 2458 l., `app.py` 2184 l., `circulation_analysis.py` 1057 l., `coverage_analysis.py` 352 l., `detection_config.py` 232 l.). Tout refactoring sur ces modules est aujourd'hui à l'aveugle.
2. **Dépendance circulaire** `olm/ingestion/extract.py` ↔ `olm/ingestion/test_comb.py`, avec `test_comb.py` qui n'est ni un test ni un module produit (2321 lignes hors `olm/tests/`).
3. **`olm/server/app.py` monolithique** : 2184 lignes, 35 endpoints, mélange routes / parsing / logique métier / sérialisation.
4. **70+ `addEventListener` sans `removeEventListener`** côté front. Pas critique tant que la session est courte, mais loi du « stack qui grandit » à chaque ouverture de pièce / changement de tab.
5. **Défauts px en dur dans `test_comb.py` L52-62** (`BINARIZE_THRESHOLD = 140`, `COMB_STEP_PX = 5`, etc.) : l'audit constantes-rustines du 2026-05-13 a flaggé ces points en 🔴, **aucun n'a été corrigé depuis**. Tant que ces défauts existent, un chemin qui oublie `_apply_detection_config` reste silencieusement faux à une échelle inattendue.

## 2. Findings — Architecture back-end Python

### 2.1 🔴 Dépendance circulaire `extract.py` ↔ `test_comb.py`

**Fichiers** : `olm/ingestion/extract.py` (2458 l.) ↔ `olm/ingestion/test_comb.py` (2321 l.)

**Constat**
- `extract.py` importe de `test_comb.py` : `detect_room`, `_apply_detection_config`, `COMB_STEP_PX` (lignes 1596, 2201, 2203).
- `test_comb.py` importe de `extract.py` : `_classify_wall_direct` (ligne 2018).
- Le nom `test_comb.py` suggère un fichier de test, mais c'est un **module utilitaire / algorithme** (raycasting peigne, détection de pièce) avec un `def main()` ligne 2343 et de la logique exécutable.
- Il n'est pas dans `olm/tests/` → la convention `test_*.py` est trompeuse.

**Impact**
- Toute modification de l'un casse l'autre sans le compilateur Python pour le détecter (Python tolère les imports circulaires à l'exécution mais introduit des `ImportError` à des moments imprévisibles).
- Confusion permanente : un nouveau contributeur cherche le test, trouve 2 300 lignes d'algo.
- Bloque le découpage propre du pipeline d'ingestion.

**Recommandation**
1. Renommer `olm/ingestion/test_comb.py` → `olm/ingestion/comb_detection.py` (ou `comb_algorithm.py`).
2. Extraire la logique partagée (`_classify_wall_direct` notamment) dans un troisième module `olm/ingestion/wall_classify.py` importé par les deux.
3. Si des assertions exécutables existent dans `test_comb.py`, les déplacer vers `olm/tests/test_comb_detection.py`.

**Effort** : 6-8 h (déplacement + tests de régression manuels sur un plan de référence).

### 2.2 🔴 Monolithe `olm/server/app.py` (2184 lignes, 35 endpoints)

**Constat**
- 55 fonctions, 35 routes Flask, ~6 rôles mélangés : parsing JSON, logique OCR, détection fenêtres, matching, sérialisation `RoomSpec → JSON`, CRUD catalogue, gestion config projet.
- Exemple : endpoint `POST /api/room/reanalyze` (L1367-1469, ~102 lignes) mélange parsing du payload, appel à `extract_room_features`, OCR, conversion coordonnées, sérialisation.
- Chargement config inline en haut du fichier (L46-122 : `_load_project_config`, `_get_plans_dir`, `_get_detection_overrides`).
- 35 routes vues lors de l'audit (à confirmer par grep `@app.route`).

**Impact**
- Modification = risque élevé de casser plusieurs endpoints non liés.
- Tests d'intégration impossibles à scoper proprement (où finit le routage, où commence le métier ?).
- Pas de réutilisation possible des helpers (ils sont privés au fichier).

**Recommandation** : extraire en `olm/server/services/` :

```
olm/server/
├── app.py                  # Flask routes + délégation (< 500 lignes cible)
└── services/
    ├── ingestion_service.py   # extract + reanalyze + OCR
    ├── matching_service.py    # match_room, desk positions
    ├── catalogue_service.py   # CRUD patterns
    ├── config_service.py      # load_project_config, get_detection_overrides
    └── serialization.py       # RoomSpec ↔ JSON, MatchScore ↔ JSON
```

**Effort** : 16-20 h (extraction + tests d'intégration sur les endpoints clés).

**Prérequis** : créer **avant** des tests d'intégration sur les 5-10 endpoints les plus critiques (`/api/room/reanalyze`, `/api/floor-plan/match`, `/api/plans/<id>/save`, etc.) pour ne pas faire le refactor à l'aveugle.

### 2.3 🟡 Fragmentation des 5 modules de configuration

**Fichiers**
- `olm/core/app_config.py` (144 l.) — loader central, persistance.
- `olm/core/matching_config.py` (20 l.) — `GRID_CELL_CM`, `MIN_DESKS_DROP_RATIO`. Wrapper d'`app_config`.
- `olm/core/spacing_config.py` (123 l.) — dataclass `SpacingConfig`, 3 standards.
- `olm/core/detection_config.py` (232 l.) — dataclass `DetectionConfigCm`, 40+ tolérances OCR/raster.
- `project/config.json` — config disque.

**Constat**
- `matching_config.py` ne contient que 2 getters (`GRID_CELL_CM = app_config.get(...)` et `MIN_DESKS_DROP_RATIO = app_config.get(...)`). Pas de logique métier, pas de dataclass.
- `app_config.py` charge `config.json` une fois au import. C'est le bon endroit pour les getters typés.
- `spacing_config.py` est légitime (vraie dataclass, méthodes `from_dict`/`to_dict`).
- `detection_config.py` est légitime (domaine OCR/raster, conversion cm→px).
- **Chevauchement** : `binarize_threshold` existe à la fois dans `detection_config.py` (défaut 140) et `project/config.json` (`ingestion.binarize_threshold = 110`). Deux valeurs différentes selon le chemin. `test_comb.py` L52 utilise encore 140 en dur.

**Recommandation**
1. **Fusionner `matching_config.py` dans `app_config.py`** — 2 getters n'ont pas besoin d'un module.
2. **Trancher la source unique pour `binarize_threshold`** : `project/config.json` est la source disque, `detection_config.py` est la source par défaut. Aligner les défauts ou documenter l'intention.
3. Documenter en tête de `app_config.py` la hiérarchie : `project/config.json` (disque) → `app_config.py` (loader) → `DetectionConfigCm.from_dict()` (consommateur).

**Effort** : 2-3 h.

### 2.4 🟢 Points bien faits

- **Pas d'import `from project`** : la séparation `olm/` (open source) ↔ `project/` (privé) est respectée. Les chemins vers `project/` sont résolus dans `app.py` via `BASE_DIR`.
- **`app_config.py` n'importe rien de `olm.core`** (commentaire défensif L9-10) : isolation correcte de la racine de dépendances.

### 3.2 🔴 Gestion d'erreurs trop générique

**Fichier** : `olm/server/app.py`

**Constat** : 12 occurrences de `except Exception: ... traceback.print_exc()` (lignes 372-374, 449-451, 574-576, 590-592, 647-649, 817, 1017, 1465, 1587, 1637, 1736, 1872).

**Impact**
- `traceback.print_exc()` écrit sur stderr, **pas** dans le logger configuré → invisible en production / dans les logs structurés.
- `except Exception` masque les bugs de programmation (TypeError, AttributeError) au même titre que les erreurs métier attendues.

**Recommandation**
- Remplacer **toutes** les occurrences par `logger.exception("contexte: ...")` ou `logger.error("...", exc_info=True)`.
- Quand une exception attendue est claire (ex. `FileNotFoundError`, `json.JSONDecodeError`), la catcher spécifiquement.

**Effort** : 2 h (mécanique).

**Constat**

### 4.2 🔴 70+ `addEventListener` sans `removeEventListener`

**Constat par fichier**

| Fichier | `addEventListener` | `removeEventListener` |
|---|---|---|
| `ingestion.js` | 34 | 0 |
| `init_rvtool.js` | 21 | 0 |
| `catalogue.js` | 7 | 0 |
| `editor.js` | 7 | 0 |
| `config.js` | 5 | 0 |
| `init.js` | 3 | 0 |
| **Total** | **~77** | **0** |

**Impact**
- Memory leak progressif : chaque ouverture de pièce / changement de tab / re-render ajoute des listeners sans nettoyer les anciens.
- Listeners dupliqués sur re-render : double-handler possible sur `catalogue.js:92-100` (re-bind à chaque `renderCatalogue()`).
- Risque NRE si listener garde une référence à un DOM disparu (cas notable : `init_rvtool.js` 6 listeners `document` globaux jamais nettoyés sur sortie du mode Room amend).

**Recommandation**
1. **Pattern à généraliser** : stocker les listeners dans des variables nommées, exposer un `_dispose()` par module.
   ```js
   var _handleRvMousedown = function(e) { ... };
   rvCvEl.addEventListener('mousedown', _handleRvMousedown);
   // sortie :
   rvCvEl.removeEventListener('mousedown', _handleRvMousedown);
   ```
2. Pour `catalogue.js` : utiliser **event delegation** sur un parent unique au lieu de `querySelectorAll(...).forEach(addEventListener)` à chaque render.
3. Pour `init_rvtool.js` : appeler `_dispose()` dans la sortie de Room amend.

**Effort** : 6-8 h sur les 3 fichiers les plus chargés.

## 9. Conclusion

OLM est un prototype **mature dans son cœur métier**, avec une architecture canonique pièce/pattern de bonne qualité, des conventions Python rigoureuses et un front-end vanilla bien organisé pour sa taille. Les audits précédents (2026-04-21, 2026-05-13) ont été **largement appliqués**, ce qui démontre une capacité de discipline du projet.

Les fragilités identifiées sont **concentrées sur les couches d'orchestration** : un serveur Flask monolithique sans tests, un pipeline d'ingestion couplé en cycle à un faux fichier de test, et des défauts en dur qui devraient être lazy. **Aucune de ces fragilités n'est ingérable** — elles relèvent toutes du chantier P0/P1 documenté §7, pour ~65 h cumulées.

**Priorité absolue avant tout autre chantier** : créer les tests d'intégration sur `app.py` et `extract.py` (P0.1 + P0.2). Sans ces filets, le projet continuera à découvrir ses régressions en production sur des plans réels — exactement le pattern d'incident observé sur les K-* en 2026-05-08.
